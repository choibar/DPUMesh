# gRPC 64B echo: transport·adapter 변경 전후 — 2026-10-01

판정: **최대 처리량은 main과 같다(DPU proxy 1 core의 L7 천장). 개선은 지연과 conn 1개의 처리량이다. 요청 1개씩의 왕복은 Go에서 절반 가까이 줄었다.**

- 측정 구간 RPC 4,800,373건, 46회 실행 모두 유효했다. Payload 불일치, RPC 오류, 재연결은 0건이다. DPU proxy의 ERR, DPA 크래시, panic도 0건이다.
- L7, conn 1×64: main 11,272 → PR 12,980 RPC/s (+15%).
- L7, conn 4×64(동시 256): main 15,808, PR 15,738 RPC/s. 둘 다 proxy 1 core의 천장이다.
- L7, 요청 1개씩: p50 1,114 → 622 µs, p99 3,196 → 1,287 µs. 처리량은 764 → 1,498 RPC/s로 늘었다.
- L4, conn 1×64(1회): main 44,441 → PR 93,158 RPC/s (+110%).
- C++ gRPC는 같은 조건에서 Go의 88–98%다. 동시 256에서는 Go와 같은 천장(15,406)이다.
- 리뷰어가 측정한 9/26 코드를 이 장비에서 돌리면 1×64는 12,755로 리뷰어의 jet1 수치(12,796)와 같고, 4×64는 16,151로 jet1(19,498)보다 17% 낮다. 같은 장비에서 PR은 9/26 코드보다 1×64에서 2% 높고 4×64에서 3% 낮다.

## 빌드

host와 DPU를 같은 쌍으로 바꿔 끼웠다. session protocol이 v1과 v2로 달라 main의 host와 PR의 DPU는 섞을 수 없다.

| 빌드 | host | DPU (transport + proxy) | 보여주는 것 |
|---|---|---|---|
| M | main `8d5dd9b` (리뷰어의 Go adapter) | main, proxy `c09915bf` | 기준선 |
| C | PR의 core까지 (`78da0a6`): 새 core + 리뷰어의 Go adapter | PR, proxy `6403a4d7` | core 변경의 효과 |
| G | PR의 Go까지 (`ba24d01`): 새 core + 새 Go adapter | PR | Go adapter 변경의 효과 |
| F | PR 끝: C++ channel-bench | PR | C++ gRPC |

C와 G는 같은 core에서 리뷰어의 Go 대기 방식(dpu-dma에서 Go timer backoff)과 PR의 방식(EQ fd를 netpoller로 대기)을 비교한다.

## 결과 (L7)

RPC/s와 client가 잰 지연이다. 동시 64와 256, 1개는 3회 중앙값이고, 2·3·4 conn × 64는 1회다(C++ 1×1도 1회).

| 조건 | M | C | G | C++ (F) |
|---|---:|---:|---:|---:|
| 1 conn × 64 | 11,272 | 11,562 | **12,980** | 11,420 |
| 2 conn, 총 64 | 11,751 | 11,750 | 12,421 | 11,288 |
| 3 conn, 총 64 | 11,729 | 11,793 | 12,068 | 11,178 |
| 4 conn, 총 64 | 11,536 | 11,713 | 11,902 | 11,000 |
| 4 conn × 64 (총 256) | 15,808 | 15,874 | 15,738 | 15,406 |
| 1 conn × 1 | 764 | 765 | **1,498** | 1,149 |

| 지연 p50 / p99 (µs) | M | C | G | C++ (F) |
|---|---:|---:|---:|---:|
| 1 conn × 64 | 5,748 / 7,105 | 5,693 / 7,070 | 4,935 / 6,267 | 5,703 / 6,876 |
| 4 conn × 64 | 16,334 / 20,389 | 16,299 / 20,852 | 16,336 / 20,610 | 16,737 / 21,135 |
| 1 conn × 1 | 1,114 / 3,196 | 1,111 / 3,198 | **622 / 1,287** | 863 / 1,067 |

- **천장:** 모든 조건에서 DPU proxy가 94–97%로 busy poll했다. Host의 client와 server는 각각 0.2–0.9 core만 썼다. 동시 256에서 네 빌드가 15.4–15.9k로 모이는 것은 proxy의 L7 처리 한계다.
- **core 변경 (M → C):** 처리량과 지연이 같은 범위다(+0–3%). Idle wake의 nap 때문에 작은 ping-pong이 느려질 수 있다는 우려([idle wake 기록](2026-09-30_host-idle-wake.md))는 이 측정에서 나타나지 않았다.
- **Go adapter 변경 (C → G):** 동시 64에서 +2–12%, 요청 1개씩에서 p50 −44%, p99 −60%다. 처리량 증가는 conn이 적을수록 크다. 같은 동시성에서 왕복이 짧아진 만큼 closed loop의 처리량이 는다.
- **C++:** 천장에서는 Go와 같다. 동시 64에서는 Go의 88–93%이고, main의 Go와는 비슷하다(95–101%). C++ adapter는 이 PR에서 대기 방식이 바뀌지 않았다.

## 결과 (L4, 참고)

Proxy가 HTTP/2를 종단하지 않으면 host 쪽 차이가 그대로 보인다. 각 1회다.

| 1 conn × 64 | RPC/s | p50 / p99 µs | client / server CPU |
|---|---:|---:|---:|
| M | 44,441 | 1,461 / 2,850 | 103% / 115% |
| G | 93,158 | 640 / 1,493 | 254% / 272% |

## 리뷰어 측정과의 관계

리뷰어의 jet1 측정은 9/25–26의 코드(DPUMesh `ec72182`, proxy `90915213`)였다. 같은 코드를 이 장비에서 빌드해 같은 조건으로 쟀다(host와 DPU 모두 그 코드, 서비스 주소는 당시 방식대로 registry 파일).

| 조건 | 9/26 코드 | main | PR (G) | 리뷰어 jet1 |
|---|---:|---:|---:|---:|
| 1 conn × 64 | 12,755 (1회) | 11,272 | 12,980 | 12,796 |
| 4 conn × 64 | 16,151 (2회: 16,081, 16,221) | 15,808 | 15,738 | 19,498 |
| 1 conn × 1, p50 | 934 µs (1회) | 1,114 µs | 622 µs | – |

- **1×64:** 9/26 코드는 이 장비에서도 리뷰어 수치와 같다. 그 뒤 main이 12% 느려졌고(9/28 변경과 `8d5dd9b` 중 무엇 때문인지는 가르지 않았다), PR이 이를 회복해 9/26보다 2% 높다.
- **4×64:** 9/26 코드도 이 장비에서 16.2k다(jet1 19.5k). 같은 장비의 PR은 9/26보다 3% 낮다(회차 2–3회라 편차와 비슷한 크기다). 같은 시간대에 main을 한 번 더 쟀을 때 15,886이었다.
- **host CPU:** 9/26의 Go adapter는 in-line polling이라 server가 약 1 core(104%)를 썼다. PR은 같은 4×64에서 0.5 core(49%)다.

**측정 중 발견:** `linkerd2-proxy/scripts/dev-proxy-env.sh`는 proxy 로그를 `linkerd=debug`로 둔다. 이 스크립트를 먼저 source한 뒤 기본값을 주면 debug가 남는다. 그러면 L7은 요청마다 DEBUG 로그 2줄을 쓰고 처리량이 6.9k로 떨어진다(20초에 107 MB). `bench/grpc/dpu/env.sh`는 source 전에 `warn`을 둔다.

## 조건

| 항목 | 설정 |
|---|---|
| 장비 | host rapids4 (Xeon Gold 6554S), BF-3, DOCA 3.1.0105. DPU 03:00.0 / host 94:00.0. 03:00.1에서는 다른 DPA job이 계속 실행 중이었다 |
| Proxy | worker 1개, `LINKERD2_PROXY_CORES=1`, busy poll, 로그 warn. 모든 thread를 DPU CPU 11에 고정하고 mock은 CPU 7–8에 두었다. `MOCK_POLICY_ECHO_TARGET=1`, profile network는 dev 기본값 |
| DPA | PR 빌드는 `DPUMESH_DPA_EU_BASE=64`. main에는 이 설정이 없다 |
| Reverse | `dpu-dma` |
| Host | client CPU 18–25, server CPU 26–33(BlueField function의 NUMA node). Go는 `GOMAXPROCS=8`, C++은 reactor 1개 |
| Workload | channel-bench, 64B raw unary echo. 응답마다 전체 비교. Backend pool은 conn 수와 같다 |
| 구간 | 연결별 preflight → warmup 3초 → 측정 10초. 실행마다 proxy와 mock을 새로 띄웠다 |
| 순서 | 1회차는 빌드마다 6개 조건을 차례로, 2–3회차는 핵심 3개 조건만 빌드를 번갈아 돌렸다 |

Host 라이브러리 SHA-256 앞부분: M `f9acf220`, C `e8cc64a2`, G `52dd216c`, F `0183e4a0`. DPU proxy: main `8a725030`, PR `c383679b`. DPA kernel archive: main `ee12652a`, PR `f1f7889f`.

## 하지 않은 것

- 장시간 지속 부하(DPA 크래시 확인)와 idle CPU는 이번에 재지 않았다. idle CPU는 [idle wake 기록](2026-09-30_host-idle-wake.md)에 있다.
- `host-dpa` reverse는 이 장비에서 host DPA process를 만들 수 없어 재지 않았다.
- 2·3·4 conn × 64(총 64)는 1회씩이다.
