# gRPC 64B echo: Node.js 서버 — 2026-10-01

판정: **Node.js 서버는 conn 1×64에서 Go 서버의 84%, conn 4×64에서 94%다. 차이의 대부분은 grpc-js가 요청마다 JS thread 하나에서 하는 처리이며, DPUMesh binding을 바꿔서 줄일 수 있는 몫은 약 2%다.**

- grpc-js에는 client transport hook이 없어 Node.js는 서버만 잰다(Online Boutique의 currency, payment도 서버다). Client는 Go channel-bench다.
- 측정한 실행 모두 유효했다. Payload 불일치, RPC 오류, DPU ERR·크래시는 0건이다.

## 결과

L7, DPU proxy 1 core, 64B unary echo. Go client → 각 서버. Node는 3회 중앙값, 나머지는 1회다(Go 서버는 같은 시간대에 잰 값).

| 서버 | 1 conn × 64 | Go 대비 | p50 / p99 | 4 conn × 64 | 1 conn × 1, p50 |
|---|---:|---:|---:|---:|---:|
| Go | 12,782 | 100% | 5.0 / 6.4 ms | 15,670 | 622 µs (오전 측정) |
| C++ (Node와 같은 stream reactor) | 12,162 | 95% | 5.3 / 6.4 ms | – | 735 µs |
| Node.js, preload (진짜 socket) | 10,964 | 86% | 5.8 / 9.2 ms | – | 845 µs |
| **Node.js, adapter** | **10,767** | **84%** | 5.8 / 11.2 ms | **14,747 (94%)** | 952 µs |

TCP(Go client → Node.js 서버, DPU 없음, 1회): 1×64 29,914, 4×64 30,883 RPC/s, 1×1 p50 103 µs.

## 원인

- **stream reactor:** 서버만 C++로 바꾸면 Go의 95%다. 공통 C++ reactor(stream C ABI)의 몫은 약 5%다.
- **CPU 포화는 아니다:** 1×64에서 JS main thread가 36%, GC thread가 각 2%를 썼다. 요청당 process CPU는 DPUMesh 44 µs, TCP 38 µs로 비슷하다.
- **단일 JS thread의 직렬 처리가 지연이 된다:** 요청 하나에 JS thread가 약 33 µs를 쓴다. 64개가 한꺼번에 오면 뒤의 요청이 앞의 처리를 기다리고, closed loop에서는 그 지연이 처리량 감소로 이어진다(p50 +0.8 ms, p99 +4.8 ms). Proxy가 먼저 포화되는 4×64에서는 차이가 6%로 줄어든다. 같은 직렬 처리는 TCP에서도 있지만(1×64 p99 7 ms), 왕복이 짧아 처리량에 덜 드러난다.
- **binding 몫:** 같은 Node.js 서버를 preload로 붙여 Node.js가 진짜 socket 위에서 HTTP/2를 쓰게 해도 처리량은 2%, 1×1 지연은 107 µs만 좋아졌다. JS stream wrapper와 thread 전환을 없애는 binding 개선의 대략적인 상한이다.
- **시도한 개선:** reactor 이벤트를 큐에 모아 JS로 한 번에 넘기게 바꿔 보았다. 1×64 10,756 / 10,846, 1×1 950 / 953 µs, 4×64 14,645로 차이가 없어 넣지 않았다.

남은 차이를 줄이는 방법은 Node.js 서버 프로세스를 여러 개 두는 것(cluster)이다. 이번 비교 조건(언어마다 서버 프로세스 하나)과 달라서 재지 않았다.
