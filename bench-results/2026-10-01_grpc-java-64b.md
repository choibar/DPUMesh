# gRPC 64B echo: Java — 2026-10-01

판정: **Java는 conn 1×64에서 Go의 87%(Java끼리)와 91%(Go client → Java 서버), conn 4×64에서 99%다. 측정 중 Java binding이 한 번에 flush한 HTTP/2 frame을 따로 써서 요청마다 약 1 ms를 더하던 문제를 찾아 고쳤다.**

- Online Boutique의 adservice처럼 Go client가 Java 서버를 부르는 구성은 1×64에서 91%다.
- 측정한 실행 모두 유효했다. Payload 불일치, RPC 오류, DPU ERR·크래시는 0건이다.

## 결과

L7, DPU proxy 1 core, 64B unary echo. "수정 전"은 3회 중앙값이다. "수정 후"는 Java끼리 1×1과 1×64가 2회, 나머지가 1회다. Go끼리는 같은 시간대에 잰 값이다.

| client → server | 1 conn × 64 | Go 대비 | 4 conn × 64 | Go 대비 | 1 conn × 1, p50 |
|---|---:|---:|---:|---:|---:|
| Go → Go | 12,979 | 100% | 15,732 | 100% | 622 µs (오전 측정) |
| Go → Java, 수정 전 | 11,989 | 92% | – | – | 1,791 µs |
| **Go → Java, 수정 후** | **11,864** | **91%** | – | – | **956 µs** |
| Java → Go, 수정 전 | 11,630 | 90% | – | – | – |
| Java ↔ Java, 수정 전 | 10,804 | 83% | 15,007 | 95% | 2,674 µs |
| **Java ↔ Java, 수정 후** | **11,270** | **87%** | **15,519** | **99%** | **1,499 µs** |

TCP(Java끼리, DPU 없음, 1회): 1×64 78,688, 4×64 225,457 RPC/s, 1×1 p50 109 µs.

## 찾아서 고친 문제

- **현상:** 요청 1개씩의 지연이 Java 쪽 한 번에 약 1 ms씩 더해졌다. 같은 stream reactor를 쓰는 C++, .NET, Node.js 서버는 735–952 µs인데, Java 서버는 1,791 µs였다. Online Boutique 측정에서도 ad(Java)가 가장 느렸다.
- **원인:** grpc-netty는 HTTP/2 frame마다 ByteBuf를 따로 넘기고, binding은 이를 하나씩 `dms_stream_write`로 썼다. 앞 frame이 전송 중이면 libdpumesh는 새로 쓴 작은 unit을 tail deadline(500 µs) 또는 ack까지 붙잡는다. 그래서 뒤 frame이 기다렸다. Node.js(`_writev`)와 .NET은 한 번에 모아 써서 이 영향이 없었다.
- **수정:** `DpumeshChannel.doWrite`가 flush된 ByteBuf 가운데 native post 하나에 들어가는 앞부분을 한 버퍼로 모아 한 번에 쓴다. 큰 frame은 전과 같이 따로 쓴다.
- **효과:** 요청 1개씩 p50이 Java끼리 2,674 → 1,499 µs, Go → Java 1,791 → 956 µs다. 처리량은 Java끼리 1×64 +4%, 4×64 +3%다(4×64는 1회).

남은 차이는 다음과 같다. Java 서버의 1×1 지연은 Node.js 서버(952 µs)와 같고 C++ 서버(735 µs)보다 약 220 µs 길다. Java끼리 1×1은 .NET끼리(888 µs)보다 600 µs 길어서 Java client 쪽에도 추가 지연이 남아 있다. 이번에는 원인을 보지 않았다.
